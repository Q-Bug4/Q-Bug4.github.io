# 模型值班部署手册

适用范围:6× DGX Spark(GB10)推理集群,团队定期部署热门开源模型的值班流程。
本手册是活文档,每次值班发现新坑/新经验,值班人负责更新本页。

## 一、节奏

- **双周一个值班窗口**,一人主责,不追每周热点
- 原因:新模型发布后需要等两样东西成熟——社区量化版(NVFP4/GGUF,通常 3-7 天)、
  推理引擎适配(vLLM recipe / Spark sm_121 镜像,参考 Gemma 4:4/2 发布,4/10 才有
  能跑的镜像)。双周窗口正好卡在"坑已被社区踩过"的时点,值班人是复刻者,不是小白鼠

## 二、选型标准(五条全过才排期)

1. **HF 官方权重 + 许可干净**:Apache 2.0 / MIT 优先;区域限制类许可(如 MiniMax H3
   的 Community License 对美/欧/英/韩主体有附加要求)先过确认再用
2. **架构适合 GB10**:MoE 低激活或 ≤35B dense 单机可跑;更大模型需已有 TP 方案
   (参考 mimo-v25 双机方案)
3. **目标 >40 tok/s**(单机或 2 机可达);达不到只做评估记录,不进部署排期
4. **社区已有 Spark/GB10 实测**:NVIDIA 论坛 GB10 板块搜得到帖子;完全没人跑过的
   架构不排期(首次踩坑成本远超双周窗口)
5. **不与现役阵容重叠**:现有覆盖——全模态(Nemotron-3-Nano-Omni)、视觉
   (Qwen3-VL-30B-A3B)、代码(Qwen3-Coder-Next)、语音(Qwen3-Omni)、双机全模态
   (MiMo-V2.5)。新模型要么补空白模态,要么在同类别有显著优势(需附 benchmark 对比)

## 三、值班产出(四件套,缺一不算完成)

1. **可复现 recipe**:docker compose 或 systemd,参数全部固化
   (参考 ~/ai-infra/mimo-v25/ 的格式:镜像 tag、环境变量、启动参数、.env.example)
2. **冒烟测试脚本**:文本 + 该模型支持的各模态各一条 curl 请求,一键跑通
3. **Benchmark 记录**:`vllm bench serve`,单流 + c=4 + c=8,与现役同类别模型
   同条件对比。⚠️ 客户端 SSE 会低估 ~40%,以服务端日志为准
4. **调研文档**:走博客草稿流程——`hexo new draft` → 打 `AI生成` 标签 + 声明块 →
   人工审核后发布。值班人署名,作为交接载体

## 四、发布流程(权限分级)

```
HF 调研 → 选型五条 → 评估机部署 → benchmark 评审 → 网关注册灰度 → 生产
                        ↑ 值班人权限到这里
```

- **评估机**:固定 1 台 Spark,值班模型先上这里,不影响生产
- **评审**:同题对比(同一段代码/同一张图/同一段音频),对照现役模型
- **通过**:注册 LiteLLM 网关命名后端(命名规范:`spark-<模型短名>`,如 spark-glm53),
  先灰度内部团队,观察一周
- **生产上线由 Kael 手动执行**,值班人没有 push/生产部署权限(与博客发布规则一致)

## 五、轮换与交接

- 2-3 人轮,每人一个双周窗口,简单顺序轮转
- 每窗口**主备两人**:
  - 主责:部署 + 四件套
  - 备份:只做一件事——照主责的 recipe 从零复刻一遍。复刻失败 = recipe 不完整,
    退回主责补文档后重新复刻
  - 这条强制保证知识沉淀,避免"只有部署的人会运维"
- 交接:在博客草稿评论区 @ 下一位值班人,公开可查

## 六、信息源清单(值班首日先扫一遍)

| 来源 | 用途 |
|---|---|
| NVIDIA 论坛 DGX Spark / GB10 板块 | 新模型实测最先出现的地方,含 recipe 和坑 |
| HuggingFace trending + 官方 org(Qwen、google、nvidia、zai-org) | 权重发布第一手 |
| sparkbench.dev | GB10 性能榜单,看哪些模型值得追 |
| vLLM recipes 仓库 + vllm-omni | 官方部署配方 |
| Unsloth / RedHatAI / ig1 等 HF 量化组织 | NVFP4/AWQ 量化版到位情况 |

大新闻(GLM/DeepSeek/Qwen 新旗舰)出 NVFP4 Spark 版,基本都是上述渠道先报。
